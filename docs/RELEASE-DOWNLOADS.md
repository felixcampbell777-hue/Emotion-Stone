After the integration owner freezes a source commit and authorizes the initial push:

1. Push only the working handoff branch; its branch-limited push trigger starts **Native release checks** automatically. Keep the exact run/commit URL with the release evidence.
2. Finish the local native macOS visual/runtime checks and regenerate its validated client export from that same frozen source. Retrieve the Windows and Linux CI reports/packages. Inspect the Linux eight-client performance report honestly; successful functionality alone does not establish a 60Hz budget.
3. Place the matching target packages in their normal ignored output directories and invoke `python3 tools/prepare_release_downloads.py --native-report <Windows-report> --native-report <Linux-report>`. This rejects stale fingerprints, failed/mismatched native gates, skipped validation, missing executables, altered package files and mismatched Compose versions. It never replaces an existing assembled release folder.
4. Review `output/releases/v<VERSION>/game/` and `server/`. Each contains ready-to-use ZIP downloads, instructions, a source/native-gate manifest and SHA256 checksums. The server ZIP includes its Linux executable, durable helper, notices, pinned Docker inputs, supervision/admin/backup helpers and operations guide; hosting requires no source clone or Godot installation. The macOS exported ZIP is preserved intact to retain its app metadata/signature.
5. The integration owner reviews the complete local/CI evidence and grants the publication gate. Publish separate GitHub prereleases for the two new tags; attach only the files from the corresponding game/server folder. Never upload secrets, userdata, logs containing private identities or toolchain-local records. Do not claim public distribution notarization, physical microphone listening or Windows GPU/device play from headless tests.

The assembler records remaining human/device/notarization limits and labels the deliverables prereleases. It does not replace visual/gameplay acceptance, the model approval gate or any required asset audit. Existing candidate manifests remain honest about those separate gates. No push, tag or GitHub release is created by the assembler.

Before the initial native-CI push, run `python3 tools/verify_local_release.py --docker` on macOS after all three validated exports. It checks all package manifests against the frozen runtime, verifies a fresh extracted app signature/version, executes its actual title/Host/native-capture/codec/playback fixtures without a source path override, then uses a disposable Docker project and loopback ports 24891/24892 for Linux release guards, packaged synthetic voice and two returning packaged profiles across a clean server restart. The current report is `output/verification/local-release-current.json`. Test secrets, userdata, containers and volumes are removed, including on failed checks; existing same-named fixture resources are refused. Native microphone tests do not request OS permission and do not establish human listening quality. Docker on Apple arm64 emulates the Linux x86_64 target; native Linux performance still comes from its separately scoped CI report.
